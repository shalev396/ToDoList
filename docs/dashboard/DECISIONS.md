# DECISIONS.md

Decisions taken while building TodoList from the Elytra template. Where the design docs in this folder were ambiguous, silent, or overtaken by Shalev's later instructions, the choice made and the reason are recorded here.

- **Plan:** [`docs/superpowers/plans/2026-11-11-todolist-dashboard.md`](../superpowers/plans/2026-11-11-todolist-dashboard.md)
- **Precedence among the docs:** DATA.md decides names, BUILDER.md decides block schema, and MCP.md decides tool names.

## Changes of direction requested after the docs were written (2026-11-11)

| # | Change | Effect |
|---|---|---|
| C1 | **Multi-user service.** TodoList is a free service for classmates and anyone else, not a single-user app. | When users log in, they create an organization or join one they were invited to. One organization can have many users, and one user can belong to many organizations. The code and API keep the `Workspaces`/`Memberships` names; the UI says "Organization". |
| C2 | **GitHub connection.** Projects boards, repos, issues/PRs and org repos. | See the plan's "GitHub connection" section. One integration per owner. The credential is `{token, projectsToken?}`, because fine-grained tokens can't read Projects boards owned by a user account. |
| C3 | **New design across the whole app.** Inspired by Linear, Trello and Todoist. | Elytra appears only in the footer ("Built on Elytra"). We adopt patterns from those products, not their assets. |
| C4 | **Development first.** | A local run against the dev database string Shalev pastes into `server/.env.local`, with dummy data. qa and prod stay as the template configured them. |

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Import with `git archive e382dc5` (tracked files only), then `git init`, commit the raw import on `main`, and do all work on `local/dashboard`. | Uses Elytra as a template without its history or its gitignored stage secrets. |
| D2 | The app name is TodoList, slug `todolist`. That gives stacks `todolist-<stage>`, role `todolist-<stage>-api`, MCP URI scheme `todolist://` and GCal origin `todolist`. The agent-key prefix stays `elk_` and the event-id prefix stays `el`. | Avoids colliding with the live Elytra stacks. |
| D3 | Add `ENV=local`, `local-offline.ts` and `AUTH_MODE=local-dev`. Any email can sign in with the password `local-dev`. Startup is refused unless `ENV=local`. | Elytra has no offline mode, and several fake users are needed to test sharing. |
| D4 | Under `ENV=local`, local stand-ins replace AWS: S3 → `server/.local-storage/`, SES → suppressed, KMS → local master key, SQS → in-process queue. | No AWS calls during local runs. |
| D5 | The app uses whatever `DATABASE_URL` points to (Atlas dev or Docker). Tests use only `mongodb-memory-server`. | Tests never touch a real database. |
| D6 | New models follow Elytra's `definitions/` + `mongoose/` + `models/index.ts` getters. Sequelize throws `NotSupportedError`. Controllers call `services/*`; there are no `classes/` wrappers. | The new collections are Mongo-only. |
| D7 | Fix Elytra's `errorHandler`: give it 4 parameters, return `{message}` only, and never echo the request body. | With 3 parameters, Express 5 never calls it. |
| D8 | All provider calls go through one read-only HTTP client with `live` and `fixtures` transports. No provider SDKs. | One place enforces GET-only, redaction, backoff and fixtures. |
| D9 | MCP uses the v2 packages (`@modelcontextprotocol/server` 2.x) over stateless Streamable HTTP. | `@modelcontextprotocol/sdk` on npm is still 1.32. |
| D10 | Library pins: TanStack Table v8, `@dnd-kit/core` 6, FullCalendar's MIT plugins, zod 4 + Ajv 2020-12, `rfc6902`, Mongoose 8. | Stability with React 19 and strict TypeScript. |
| D11 | Templates are versioned JSON files. Dashboards get `scope.page` set to `topic` or `group`. | BUILDER §7 calls for templates as data, and course and project pages need a scope. |
| D12 | MCP's dry-run-before-write check is satisfied by a matching preview entry in `AuditLogs` from the last 10 minutes. | Lambda is stateless, so the check can't rely on memory. |
| D13 | The UI says "Organization"; the code, API and MCP keep "workspace". | Shalev's wording for users; the docs' naming for code. |
| D13a | UI now says Workspace (2026-11-12, Shalev). | Supersedes the "Organization" wording of D13; code, API and MCP are unchanged. |
| D14 | Split the vault: `credentialWriter` only encrypts, and `credentialVault` (the decrypt paths) can only be imported from an allow-list enforced by a test. | DATA.md §3.5. |
| D15 | Worker Lambdas reuse the same code bundle and the API role. The scheduler invokes the API's `sync-dispatch` action, which enqueues to SQS for the worker. | Keeps Elytra's single-bundle layer design. |
| D15a | Superseded (2026-11-14, Shalev, C0-ARCH): no worker Lambdas, no SQS, no scheduler. A background sync is an async invocation of the one function by itself; see "Architecture (C0-ARCH)" below. | A much simpler stack, like Elytra. |
| D16 | Client unit tests run on `node:test`. Postman stays only for deployed stages. | Keeps Elytra's tooling, and Cognito can't run offline. |
| D17 | Nothing user-specific lives in code. Area defaults are per integration, and connecting GitHub adds a `<login>/*` → personal rule. Demo specifics live only in the seed. | It is a service now, so code can't assume one person's setup. |
| D18 | Replace Elytra's whole visual layer. Its only remaining trace is the "Built on Elytra" footer credit. | C3. |
| D19 | **Creating** a local to-do in the user's own providers is allowed (H5, Shalev's request): Jira, ClickUp, Linear, GitHub, and Google Calendar as an event. It narrows D8's "never write to providers" to one thing: after an explicit user action TodoList may create one item in an integration the user connected, through a separate write client whose only allow-list is the exact create endpoints (Linear: the named `issueCreate` document only). It never edits, closes or deletes anything at a provider; completing or deleting the local to-do does not touch its copies. Gated by role (editor+), ownership (own integration only), `PROVIDER_WRITES_ENABLED`, 30 creates per user per provider per hour, a client request id (never two creates), an audit entry per create (no title, no token) and, for MCP, `confirm: true` plus the `providers:create` scope. A create that was sent and not answered is `unknown` and is never retried. | Shalev wants one place to add a task and have it where it belongs. Read-only sync (D8) is unchanged. |


## Rulings during the build

One line each: what was decided, why, and what it costs if wrong. The full wording lives in the build ledger.

### Data

- No Mongoose discriminators on `Items.kind`; validation is `$jsonSchema` plus TS types. Why: props vary by provider, not by kind. Cost: weaker app-level props validation.
- Dashboards get a `published` snapshot field, copied at publish. Why: viewers read the published config without replaying patches. Cost: duplicate storage per dashboard.
- Invites gain an `{email:1,status:1}` index, beyond DATA.md section 6. Why: onboarding lists pending invites by email. Cost: one extra index.
- No replica set and no multi-document transactions; dashboard versioning uses atomic conditional updates (`findOneAndUpdate` on `version`). Why: simpler local setup, Atlas unaffected. Cost: add `rs0` later if transactions are needed.
- Idempotent item create is a 24 h same-owner lookup, hardened with a permanent unique partial index after review. Why: matches the no-transactions ruling. Cost: a rare duplicate to-do on a double-submit race was accepted before the index; the index narrows it.
- Local item `source.url` is `/w/<wid>/items/<id>`; the client route `/:lng/w/:wid/items/:id` switches org and opens the item sheet. Why: local items have no provider page. Cost: none known.
- Calendar `externalId` is `<calendarId>:<eventId>`, with the raw id kept in `props.eventId`. Why: one id space across several calendars. Cost: DATA section 8 and APPSCRIPT section 2 differ from the original text (see REPORT, Spec deltas).
- Cancelled instances of a recurring series stay live with status `cancelled`; the client hides that occurrence. Why: a series keeps one record per instance. Cost: EXDATE/RDATE are ignored by the calendar block.
- A GitHub organization's `accountId` is the org login. Why: stable and readable. Cost: a renamed org needs reconnecting.
- A disconnect sets `Integrations.deletedAt` before soft-deleting the integration's items and containers. Why: the sweep and reaper can tell why a row went. Cost: a crash between steps leaves a resumable disconnect.
- `DashboardScope.groupVar` is required on group pages (course, project); group templates require `scope.area`; the file tree reads file items (`props.path`). Why: group pages need a stable key. Cost: course scoping of the file tree is parked.

### Sync

- Per-resource sweep with an optional window, via `syncResource` on Items and Containers (plus an index). Why: a partial or windowed listing must not delete records outside it. Cost: two extra fields and an index.
- At the end of a successful run, records whose `syncResource` is no longer listed are swept. Why: removed resources must not leave orphans. Cost: a bad listing could soft-delete more than intended; the sweep only runs on success.
- A per-record validation failure becomes `invalid_record` (a recorded failure), not a run failure. Why: one bad record must not stop the run. Cost: bad records are skipped until fixed.
- Delete-only records `{externalId, deleted}` need no URL and no overwrite; a repeated delete for an already-deleted copy is unchanged and not counted. Why: calendar delete signals carry no body. Cost: none known.
- Failures use the prefixed externalId; a provider query must return every record in `[from,to)`. Why: the window sweep depends on it. Cost: an adapter that under-lists loses records in the window.
- A GitHub secondary-rate-limit 403 (retry-after, remaining not 0) is `rate_limited`, not `auth_failed`. Why: `auth_failed` is sticky. Cost: none.
- Stale-run reaper: a run that has been running over 15 minutes becomes failed `timeout`; skipped runs of deleted integrations are finalized. Why: a dead worker must not block the integration. Cost: the reaper does not bump `consecutiveErrors` (parked).
- Seed fixture syncs use a clock option on `runIntegrationSync` and skip the throttles. Why: "Load demo data" was too slow. Cost: tests must pass the clock explicitly.
- "Sync now" is limited to once per 5 minutes per integration; integration PATCH has no schedule pause; re-saving the credential clears paused/error/expired. Why: free-tier protection and a simple recovery path. Cost: users wait up to 5 minutes.
- Completed Moodle activities become `done`, not deleted. Why: history stays visible. Cost: more rows.
- GraphQL partial errors use `data` and record the failures. Why: a partial board beats none. Cost: partial data can look complete until the failure is read.
- A Google Drive listing over the cap fails with `listing_too_large` (not `bad_response`). Why: an actionable code. Cost: none.

### Security

- The response guard allows JWTs only where a handler opts in via a `res.locals` allow-list (login/refresh tokens, the one-time `elk_` on key create). Why: the docs list JWT/`elk_` as leak patterns, but auth routes must return the user's own tokens. Cost: a route that forgets to opt in returns 500 in dev (loud and safe).
- The repo secret scanner ignores matches containing "FAKE" and `<placeholder>` credentials. Why: test corpora and docs need example shapes. Cost: a real token containing FAKE would pass (implausible).
- Vault identity fields (`email`, `clientEmail`, `kid`, `kidNext`) are labels, not secrets; the result scan and redaction skip them. Why: Test connection returns the account email. Cost: a provider that puts a secret in a field named `email` (none does).
- SSRF guard: a `netGuard` module checks `baseUrl`/`siteUrl` and resolved IPs, with per-hop redirect validation in the live transport. Why: a Critical review finding. Cost: legitimate private hosts are refused.
- Apps Script credential order changed: deploy first, then `setup()`, then a single PUT; rotation is a full re-PUT; `sharedSecretNext` is dropped. Why: the original two-step order left a window with a bad credential. Cost: rotation re-sends all fields.
- Invite email volume is capped; there is no `POST /me/invites/:id/accept` (the spec needs the token); the last-owner race and the invite token in the URL are accepted and recorded. Why: the token proves the email match. Cost: a token in a URL can leak via logs or history.
- Bad credential input returns 400. Why: not a 500 or a silent accept. Cost: none.
- The `ya29.` Google token pattern is added to the secret patterns. Why: cover Google access tokens. Cost: none.
- Local CORS admits any http loopback origin; the Vite `/api` proxy stays. Why: agents run on varied ports. Cost: loopback and local env only.

### MCP

- The D12 dry-run check binds to the preview: a stale preview (the dashboard changed since) no longer satisfies it. Why: a review found a stale-preview hole. Cost: a re-preview after any change.
- `builder_preview` takes its input per MCP.md section 8.4; area filters and `dryRun` on three write tools were corrected in fix round 2. Why: review findings. Cost: none.
- Agents do not hold `builder:publish`; only the UI publishes (an `allowAgentPublish` toggle goes to the agent-keys UI). Why: OVERVIEW question 9 default. Cost: agents cannot publish unattended.
- Preview-before-write goes into the MCP builder brief. Why: matches D12. Cost: none.
- MCP URL elicitation is not wired (it needs a requestState key); `sync_to_google_calendar` is an error until the bridge is enabled. Why: scoped out. Cost: manual connect-link flow.

### UI

- The UI is monochrome ink with no brand accent hue; "now" is marked in ink; the focus ring is cobalt. Why: avoids collisions with 7 source hues and reserved status hues. Cost: less brand colour; the user may want an accent.
- Elytra landing/effect component deletion moved from T4.0 to T4.1. Why: the landing keeps building until replaced. Cost: none.
- Light `--destructive` is `#c22f2f` (AA fix), recorded in DESIGN.md. Why: contrast. Cost: a slightly different red.
- Grid breakpoints follow the viewport; Up/Down move past the neighbour. Why: simple and predictable. Cost: differs from container-based breakpoints.
- Server error messages are English; the client maps known statuses and server error codes to i18n. Why: the he UI must not show English chrome. Cost: unmapped codes fall back to a generic message; the global axios toast is still English outside the app frame (parked).
- Calendar dateField `any` (startAt, or due-only dueAt), `upcoming_14d`/`7d` presets and a deadlines preset including overdue were added in T2.3; the calendar hides cancelled occurrences. Why: templates need them. Cost: none.
- Templates use block ids of at least 3 characters and explicit `$page` rules; adapters map the connected account to `assignees [connectedBy]`. Why: schema validity and a consistent owner. Cost: none.
- Free-string badge text is linted, `connect_blocks` has field/multi/static rules, and publish requires `expectedVersion`. Why: T2.3 review findings. Cost: stricter authoring.

### Permissions v2 (H1, PERMISSIONS-V2.md)

- Connectors are a block field, `connectors`: integration ids plus `local` for local to-dos. Why: the rulings name connectors as the share unit, and a field can be checked and stripped exactly, where a rule inside `where` can be nested, negated or OR-ed. The old top-level `integrationId in [...]` rule (D6) is migrated into it. A block without a connectors field reads everything its viewer may see (their own integrations, the shared ones, visible to-dos), never anyone's private data; an empty list reads nothing and the block says "No source" (fix round 1: `[]` used to mean everything, so a block emptied by Stop sharing or an edit silently widened). `update_block` takes `connectors: null` to go back to all sources; the editor offers "All sources". Cost: the sentence's provider rule is kept in step with the connectors (Logic v2 merge, below).
- Shared = the integration's id is a connector on any block of any live dashboard (drafts and published copies, private dashboards and every page), computed on every request; no stored flag. Removing a connector from a draft keeps the integration shared while the published copy still holds it, until the draft is published or the owner stops sharing (which strips both copies). Cost: one `distinct` per copy per request, served from partial (`deletedAt: null`) multikey indexes on `blocks.connectors` and `published.blocks.connectors`, and resolved once per request (services/requestMemo.ts: an AsyncLocalStorage memo that lives for one HTTP request, so one MCP call). Never cached across requests: Stop sharing must hold from the next request, and Lambda containers can't invalidate each other.
- Items and containers are keyed per integration: the natural key adds `integrationId`. Why: ruling 8 has two members connect the same account, each with their own integration; with the old key their syncs overwrote one shared copy, and visibility flipped with whoever synced last. Cost: a second copy of each record per member who connects the same account.
- Block dedup key is (provider, accountId, externalId), not (provider, externalId). Why: Jira and Moodle ids are per site, so two different sites can share a numeric id; the ruling's case (the same account) shares the accountId. The preferred copy is the block's first connector (blocks store no author; the creator picks the first connectors and later ones are appended). A block without connectors prefers the viewer's own integrations. Cost: the same Google event seen through two different Google accounts shows twice.
- Connector adds are checked per block, on every write (ops, patch, undo, redo, revert, create, template): an integration may join a block's connectors only when the actor owns it and it is live in this workspace. Another member's connector may stay or be removed (audited as `dashboard.connector_remove`), never added, so an undo that would bring back a removed foreign connector is refused too (otherwise it would re-share data its owner had stopped sharing). The refusal is 404 `integration_not_found` (the missing resource is the integration; ownership failures are never 403), the same answer for an unknown id (no existence oracle); dry runs report it as an error issue. Ownership failures on integration routes stay 404 for everyone, workspace owners included.
- Ruling 5 (duplicate a block, template from a block): neither feature exists yet. When one lands it should be a server op that copies the source block's connectors, exempt from the add check (the data is already shared); a client-side copy through `add_block` is an add and is refused for foreign connectors.
- Managing an integration (config, edit, test, sync, runs, credential, calendars, OAuth resources and reconnect, stop sharing, disconnect) needs ownership at any role, so a member moved down to viewer keeps control of their own credentials (ruling 10). Connecting needs editor or owner. MCP matches the UI: `integrations_disconnect` is its owner's at any role, with `integrations:connect` still required (the viewer role now permits that scope); `integrations_start_connect` stays at editor.
- Leaving, removal, account deletion and disconnect leave the connector ids on blocks, inert: an id whose integration is gone is the computed "A source was removed" marker (`DashboardView.connectors[id].removed`). The block editor drops such ids when the block is edited, which ends the notice; an agent editing through MCP may keep them. Stop sharing removes ids as a versioned dashboard write through the same commit as every write (history entry `stop_sharing`, so a stale edit conflicts instead of re-adding it), strips the published copy in place without publishing the draft, and marks each block it changed `sourceRemoved` ("A source was removed"; any later `update_block` clears it); a block left with no connector keeps `[]` and reads nothing. Ending a membership revokes it first (then the agent keys, then the disconnects), so a removed member can't connect or attach anything meanwhile; the member's soft-deleted integrations go through the disconnect steps again, so one that stopped part-way loses its credential and items on the next try, and an owner's `removeMember` on a former member finishes it. The dispatchers skip integrations whose owner is no longer an active member.
- Templates (ruling 16) bind the instantiating member's own integrations that match a block's static `source.provider` filter, all of them without one, plus `local` where to-dos could show; with none matching, the block gets no connectors field. This covers create-from-template, `apply_template` and topic templates. Instantiating never shares silently (fix round 1, I4): `POST …/builder/template-shares {templateKeys}` lists the actor's own integrations the templates would attach that no block holds yet; the UI asks first ("Adding X shares its items with everyone in W": "Share and create" or "Create without them"), through one hook and dialog (`useTemplateShareConfirm`) used by the gallery, + Add page and the empty state, for the persona templates to reuse. "Without them" is `shareIntegrations: false` on create, instantiate and topic create: only already-shared integrations are bound. Agents get `shares` in every dry run (builder writes, undo, create) and a sentence in the preview summary; `builder_create_dashboard` takes `shareIntegrations` too.
- Migration 17: integrations get `ownerUserId` from `connectedBy`; on live dashboards (draft and published), an old connector rule becomes `connectors`, and other data blocks get the creator's matching integrations (plus `local`), or no field when none match (it reads what each viewer may see; `[]` would read nothing); a changed dashboard's history ends at a reset snapshot, as the topics migration did, and that reset entry marks it done (a rerun skips it even after its creator connects more). A dashboard none of whose blocks matched has no marker; a rerun after a crash looks at it again. Then `orphaned-integrations` (after integration-owners) applies ruling 6 to members who left before the upgrade: each live integration whose owner has no active membership is soft-deleted, its credential hard-deleted and checked gone, its items and containers soft-deleted, audited as `integration.disconnect` by `system` (no provider revoke: that needs the credential and the network).
- Ruling 13: a filter block's options come from `GET …/facets?connectors=…`, the union of its listening blocks' connectors; one listening block without connectors means no narrowing.
- Logic v2 merge (H4): one place decides where a block's items come from, its `connectors` (the Source step). The sentence's "from [...]" stays a `source.provider` rule, so H4's sentence round-trip is unchanged, but it and the Source step's sources offer only the providers of the block's chosen connectors (all of the viewer's with "All sources"; `local` for to-dos), and changing the connectors drops provider values they no longer read. Why: the simplest option that cannot contradict the connectors and keeps the sentence tests and the rulings green. In the compiled pipeline the base access `$match` stays first, then H4's importance/attribute `$addFields`, then the filter `$match` (connectors and rules), then the dedup stages. H4's provider-field discovery samples only the items the caller may see, and its one-minute cache is keyed by that access, so Stop sharing changes it from the next request.
- The integration status view keeps exactly the binding keys (fix round 1 reverted `shared`). Which of the caller's own integrations are shared is its own owner-only call, `GET …/integrations/sharing` → `{shared: ids}`; MCP `integrations_list` answers the same as a `shared` list beside the views. An integration the owners migration missed is nobody's own (no `connectedBy` fallback), so a missed migration shows instead of hiding. The OAuth setup listing is open to any member (names and URLs only; prod blanks it). `oauth_not_owner` became `oauth_not_editor`.
- The members list keeps each member's sign-in email (workspace sharing already showed it); the leak rule's "email" is an integration account's email, which never reaches another member.
- The workspace-deleted email is English and Hebrew in one message (no language is stored per user), best effort, to the owners of the integrations the deletion removed: live ones and those `softDeleteForWorkspace` marked `deletedWithWorkspace`, so a deletion that resumes still emails them.
- A former member's private to-dos stay private: nobody can open them. Workspace owners can delete them by count only (`GET`/`DELETE …/former-member-todos`, "Delete former members' private to-dos (N)" in Members), soft-deleted and purged 30 days later, audited as `member.former_todos_delete` with the count. Their shared to-dos show "Added by a former member", and editors and owners can delete them.
- Limits: 20 integrations per member per workspace and 100 per workspace (`PLAN_LIMITS`), both 409 with their own message; an OAuth connection over a cap ends as `oauth_limit`. They hold under concurrent connects: insert, then count again with the new one, and soft-delete it over a cap (no transactions; racers may all back out, the caps are never exceeded).
- Audit entries a calendar push writes about items (`gcal.*`, target an item, `meta.integrationId`) are integration events: other members see them provider-level only, without the item id (ruling 15).

### Views, page variables and persona templates (H3, H6)

- Naming: a page's "view" (a tab) is new. It is not the older saved "View" (a saved query + viz that a block references by `savedViewId`), and not the `set_view` op, which only switches a calendar block between week, month and list. Code says `PageView`/`views[]` for tabs and keeps `SavedView` for the others.
- Storage (ruling: views live on the page's dashboard doc): `views[]` holds only the views after the Summary, `{id (vw_…), type, title, blockIds, templateKey?}`. The blocks and their layouts stay in the doc's flat `blocks` and `layouts`; a view only names its blocks, and the Summary is the blocks no view names. Why this layout instead of a grid per view: every place that already walks `blocks` (connector attach checks and share-on-attach, "Stop sharing", lint, validation, `POST /query` by block id, previews, undo/redo/revert patches, the published copy) works for views unchanged, and a block id stays unique across the page. Cost: the arrays' size cap is the page total (`CAPS.maxPageBlocks` = 40 blocks × 20 views), and the per-grid rule (40 for the Summary and for each dashboard view) is a schema check, not an array bound.
- The Summary is not stored and has the fixed id `summary`: it is always first and has no id the view ops accept (`update_view`, `move_view` and `remove_view` refuse it, 400), so it can't be removed, renamed or demoted by construction. The UI shows it as a locked first tab. Nobody picks a default view.
- Limits: `viewsPerPage` counts every view, the Summary included, so a page stores at most 19 in `views[]`; the 40-block cap is per grid. Both are enforced by `DashboardDraftSchema` (so by every write: ops, patch, restore) and mirrored in the client (`CAPS.maxViews`, `CAPS.maxBlocks`; "+ Add view" and "+ Add block" disable at the cap).
- A rigid view is exactly one block of its type (list→list, board→kanban, timeline, calendar, table, agenda, workload; the last three are new block types, also usable in a grid) and has no layout entries. Editable: its name (the view title; the block's own title is the template's), sources (`connectors`, with H1's share confirmation), filter (the shared `SentenceFilter`), sort, group-by and visible fields (`viz`), all through the one block editor ("Edit view"). A rigid view's block can't be removed on its own (`remove_view` removes both). A dashboard view is a grid like the Summary, edited with the same editor and ops (`add_block` takes an optional `viewId`).
- Ops: `add_view {type | templateKey, title?, config?}`, `update_view`, `remove_view`, `move_view`, and `viewId` on `add_block`; they are versioned, undoable and published like any op, so the agent tools (`builder_add_view`, `builder_update_view`, `builder_remove_view`) and the UI use the same path. `apply_template` with `mode: replace` keeps the views and replaces only the Summary's blocks.
- On a page of a topic, a new view reads that topic: the default query gets `topic = $page.topic` (listening to it) and the page's `topic` variable defaults to the topic, like the topic templates' own blocks. A view added with its own `config.query` is taken as given.
- Agenda and Workload: the agenda has Overdue (open tasks due before today, listed first), Earlier today (tasks due today whose time has passed), Now (only what is happening at this moment: events in progress), All day (today's all-day items), Next (the first thing still to come; everything starting in the same minute), Later today and Tomorrow, with local day boundaries in the workspace's time zone. Overdue looks back 90 days; done and cancelled tasks and past events are never listed. Workload sums hours per local day of the visible week (the workspace's week start): event lengths clipped to each day, plus the estimate of each open task due that day. An estimate is `attr.size` or a provider's story points (1 point = 4 hours, as importance uses), else `estimateHours`, else ClickUp's time estimate; unlike importance, an unknown estimate is not a default size: it counts as nothing and the task is listed under "tasks without an estimate". Days over `capacityHours` (default 8) are marked. All-day events and done or cancelled tasks count nothing. Computed in the client from the block's rows (`@api-types/workload`).
- View templates are versioned JSON in `server/src/builder/templates/views/` (my-open-work, by-status, this-week, deadlines-agenda, workload-this-week, study-dashboard), with titles in en and he and the same provider-hint binding as every template (`bindTemplateConnectors`, generalized to any `{blocks}`); `add_view` with `templateKey` binds the actor's own matching integrations, with `shareIntegrations: false` binding only already-shared ones. `POST …/builder/template-shares` now accepts view-template and persona keys as well as dashboard-template keys, so one preview and one confirmation hook cover all three.
- Persona templates are versioned JSON in `server/src/builder/templates/personas/`, listed smallest first: Light student (1 topic), Two jobs + studies + side project (4), Student + job (2). ### Architecture (C0-ARCH, 2026-11-14)

Shalev reviewed the stack in Infrastructure Composer and asked for it much simpler, like Elytra.

- No SES verification function: its Lambda, role, policy and log group, the `VerificationCheck` custom resource and the wait condition with its handle are deleted. CloudFormation dependencies order SES before Cognito instead: the CloudFront distribution depends on the three DKIM records, and the user pool on the distribution. Why: owner decision; CloudFront takes long enough to create for SES to verify. Cost: when SES is slower, the first deploy of a brand-new stage fails on the user pool and is re-run (docs/deployment.md); the rollback deletes the identity, so the re-run starts over.
- No queues: both SQS queues and DLQs, their policies, the DLQ alarms, the event source mappings and the sync and email worker functions are deleted. A background sync is an async invocation (`InvocationType: Event`) of the function by itself, named by Lambda's reserved `AWS_LAMBDA_FUNCTION_NAME`, with `{action: 'sync-run' | 'gcal-run', …}`, which lambda.ts's direct-invoke dispatcher runs (`services/syncJobs.ts`, `sync/worker.ts`); outside Lambda (`src/local.ts`) the job runs inline. The role may invoke the function by an ARN built from its name (a CDK reference would be a dependency cycle). Emails go straight to SES from the request; a failed invite email is logged and no longer retried with a rotated link (`InviteRepository.findByIdForWorker` and `rotateToken` went with the worker). One test seam, `setJobRunnerForTests`, replaces both queue senders. Why: owner decision. Cost: no DLQ: a job still failing after Lambda's two retries is dropped (its run stays `failed`, or `running` until a purge).
- No schedules for now: the four EventBridge Scheduler schedules (sync 08:00 and 18:00, the calendar every 30 minutes, purge 03:30), their group and the scheduler role are deleted, with `GCAL_SYNC_MINUTES` and the time zone. `sync-dispatch`, `gcal-dispatch`, `purge` and the other actions stay, run by a direct invoke. Why: owner decision; one schedule comes back later, done properly. Cost: until then nothing syncs, pushes to Google Calendar or purges on its own.
- One Lambda function and one role, `todolist-<stage>-api` both (Atlas maps the role ARN), with its two layers and one log group. Its timeout went from 60 seconds to 5 minutes (a sync job's, the old worker's; API Gateway still cuts HTTP at 30 seconds), and its reserved concurrency took the sync worker's 5 (dev 10, qa 15, prod 55), so the Atlas connection budget stays below the old total. The `SyncQueueUrl` and `EmailQueueUrl` outputs are gone (`KmsKeyId` stays); `@aws-sdk/client-sqs` is dropped and `@aws-sdk/client-lambda` is a runtime dependency. Why: owner decision; Elytra's shape. Cost: HTTP requests and sync jobs share one concurrency pool.
